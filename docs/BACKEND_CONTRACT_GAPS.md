# 백엔드 계약 개선 목록

프론트엔드 API 계약 복구 과정에서 확인한 서버 차단 사항이다. 프론트는 아래 데이터를 생성하거나 저장됐다고 주장하지 않는다.

## 주문과 결제

- 주문 생성과 장바구니 추가 요청에 idempotency key가 없어 응답 유실 시 서버가 exactly-once를 보장하지 못한다. 프론트는 `cart_id`와 새 cart 행을 재조회해 보수적으로 복구한다.
- 주문 생성 요청에 배송지 ID 또는 배송지 snapshot 필드가 없다.
- 주문 조회 응답에 주문 당시 상품명·이미지·옵션 snapshot이 없다.
- 장바구니와 주문 상품을 한 번에 보강할 batch 상품 API가 없다.
- 보유 쿠폰 ID를 기준으로 주문 생성 전 최종 금액을 확정하는 견적 API가 없다.
- 고객 주문 목록의 서버 상태 필터는 현재 `PAYMENT_PENDING`, `PAID`, `PLACED`, `CANCELLED`만 허용한다. 프론트는 전체 목록을 받은 뒤 나머지 정식 상태를 로컬에서 필터링한다.
- 서버 확정 결제 금액이 0원인 주문은 현재 결제 완료 요청의 `amount > 0` 검증과 충돌할 수 있다.

프론트는 기본 배송지를 참고용으로만 표시하고, 상품 상세를 고유 상품 ID별 캐시 조회로 보강한다. 결제 금액은 주문 생성 후 주문 상세를 재조회하여 계산한다.

## 회원과 운영 데이터

- `PATCH /api/v1/me`는 요청값을 저장하지 않고 현재 프로필을 다시 반환한다.
- 관리자 회원 응답에는 포인트 잔액이 없다.
- 관리자 주문 취소 요청의 사유는 저장되지 않는다.
- 범용 감사 로그의 일반 `target_id`와 `reason` 계약이 없다. 현재 관리자 감사 화면은 정산 작업 로그의 실제 필드만 표시한다.
- 관리자 회원 응답은 `PasswordHash`를 네트워크로 노출한다. 프론트 normalizer가 즉시 폐기하지만 서버 DTO에서도 제거해야 한다.

## 캠페인과 fulfillment

- 이벤트 상세 응답에 회원별 reward 수령 여부가 없어 포인트 보상은 새로고침·응답 유실 뒤 특정 수령 상태를 판정할 수 없다. 쿠폰 보상만 보유 쿠폰 ID로 검증한다.
- 캠페인 클릭은 클릭 기록만 남기며 포인트나 쿠폰 리워드를 지급하지 않는다.
- 판매자 sync-log 집계 응답에는 요청한 마켓 범위를 증명할 `market_id`가 없다. 프론트는 임의로 마켓 필터링하지 않는다.
- raw/envelope 응답과 PascalCase/snake_case가 엔드포인트마다 섞여 있다. 프론트는 엔드포인트 스키마로 대응하지만 장기적으로 서버 DTO와 오류 envelope를 통일해야 한다.
