## API·DB 계약과 배포 전제

- 주소록 조회는 구매자·판매자 각각의 토큰으로 기존 `GET /api/v1/me/addresses`를 사용한다. 판매자 도착지 저장도 기존 마켓 반품지 API를 사용한다. **판매자 주소록 선택만을 위한 새 API·DDL은 없다.**
- 구매자 신청의 선택적 `POST /api/v1/orders/{orderCode}/refunds` → `pickup`은 별도 계약 확장이다. 프론트는 유효한 값을 보내며, 서버는 형식·주문 소유권을 검증하고 신청 당시 주소를 보존한다.
- 생성·목록 응답의 `pickup`은 신청 주소 또는 `null`이다. 기존 주소 없는 요청에 배송지를 추정해 채우지 않으며, 이전 클라이언트의 필드 생략도 허용한다.
- 실제 수거 건의 `pickup`·`destination`은 신청 주소와 별도 스냅샷이다. 신청 주소록이나 마켓 기본 반품지를 바꿔도 이미 저장된 주소를 자동으로 덮어쓰지 않는다.
- `20261022001_refund_pickup_address.sql`은 `order_refunds`에 `pickup_recipient_name VARCHAR(100)`, `pickup_phone VARCHAR(20)`, `pickup_postal_code VARCHAR(10)`, `pickup_address VARCHAR(255)`, `pickup_address_detail VARCHAR(255)`를 추가한다. 모두 `NOT NULL DEFAULT ''`다.
- 이 SQL·엔터티 변경은 #200에 함께 반영한다. #198·#201은 선행 브랜치에서 해당 스키마를 상속한다. 순서는 #200 스키마 → #198 주문·결제 → #201 반품 API → #57 프론트다. 운영 DB에는 적용하지 않았다.
- 추가 SQL의 Down은 위 5개 컬럼을 삭제한다. 신청 주소를 보존해야 하는 운영 롤백에서는 이 Down을 실행하지 않고 확장 스키마와 코드 호환성을 확인한다.
- 검수 응답의 `restocked_quantity`·`restocked_at`도 필요하다. 기존 재고 이력에서 조회하므로 이 두 응답 필드 때문에 추가 컬럼을 만들지는 않는다.

## 기존 최종 영상 검증 — 2026-10-23

### 검증 범위

- 실제 Next.js 프로덕션 화면·로그인·로컬 API·Docker MySQL·로컬 Temporal을 사용했다. 배송 완료 주문·계정·주소는 합성 fixture다.
- 실패 장면은 **첫 신청 POST를 브라우저에서 서버 도달 전에 차단**해 재현했다. 정적 성공 응답을 주입하지 않았다. 실패 상태 확인 후 차단을 해제하고 실제 로컬 API로 다시 신청했다.
- PG HTTP만 로컬 대역이다. 이번 검증에서 새 실제 Toss 승인·카카오페이 인증·실계좌 환불·실물 수거는 실행하지 않았다. 수거·입고는 판매자가 실제 화면에서 상태를 기록하는 동작을 검증했다.
- 최신 실행은 기존에 필요한 스키마가 적용된 로컬 DB를 사용했다. 이번 실행만으로 빈 DB 마이그레이션·Down/Up 재검증 또는 운영 적용을 완료했다고 보지 않는다.
