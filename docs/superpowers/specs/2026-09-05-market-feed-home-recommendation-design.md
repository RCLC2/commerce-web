# 마켓 피드 전환과 홈 추천 계약 정리 설계

- 날짜: 2026-09-05
- 상태: 대화에서 방향 승인, 구현 전 문서 검토 대기
- 대상 저장소: `commerce-web`, `commerce-server`
- 웹 기준 브랜치: `feat/today-outfit-weather`
- 서버 기준 브랜치: 최신 `origin/main`에서 분리한 기능 브랜치

## 1. 배경

현재 하단 주요 메뉴의 `트렌드관`은 `/snapshot`에서 최근 검색어 순위만 보여 준다. 이 화면은 검색 화면의 인기 검색어와 역할이 겹치고, 홈의 상품 발견 경험에 비해 독립 페이지로서 제공하는 가치가 작다. 반면 서비스에는 마켓 팔로우 관계와 마켓별 상품이 있지만, 팔로우한 마켓의 새 상품을 한곳에서 보는 고객 화면이 없다.

홈의 추천 표기도 실제 동작과 다르다. 웹은 공개 `GET /api/v1/products/recommendations`를 개인화 추천처럼 사용하지만 서버는 이 경로를 `ListLatestProducts`에 연결한다. 실제 회원별 추천은 인증이 필요한 `GET /api/v1/me/recommendations`에 있고, 응답은 추천 메타데이터와 `product_id`만 제공하므로 웹의 상품 카드에 바로 사용할 수 없다.

이 설계는 트렌드관을 명시적인 팔로우 관계에 기반한 `마켓 피드`로 교체하고, 홈은 실제 회원 추천과 공개 인기 상품을 정확히 구분해 표시한다.

## 2. 제품 영역과 책임

- **홈**: CMS 편집 구좌, 이벤트, 프로모션, 광고와 회원별 상품 추천을 제공한다.
- **마켓 피드**: 사용자가 직접 팔로우한 마켓의 신상품을 최신순으로 제공한다.
- **카테고리**: 사용자가 조건을 선택해 상품을 찾는 목적형 탐색이다.
- **오늘의 코디**: 날씨와 상황을 출발점으로 상품을 탐색한다.
- **검색**: 직접 검색과 인기 검색어를 제공한다. 기존 trending API는 검색 보조 기능으로만 유지한다.
- **좋아요·장바구니·마이페이지**: 사용자의 쇼핑 상태와 거래를 관리한다.

홈 추천과 마켓 피드는 개인화라는 공통점이 있지만 입력 신호가 다르다. 홈 추천은 행동 기반 점수로 후보 상품을 재정렬하고, 마켓 피드는 팔로우한 판매처가 등록한 상품을 시간순으로 보여 준다. 마켓 피드에는 추천 점수, 광고, CMS 수동 편집을 섞지 않는다.

## 3. 목표

1. 하단 메뉴의 `트렌드관`을 `마켓 피드`로 교체한다.
2. 로그인 회원은 팔로우한 마켓의 판매 가능한 신상품을 최신순으로 본다.
3. 비로그인 또는 팔로우가 없는 회원은 마켓 발견 화면을 보고 로그인하거나 마켓을 팔로우할 수 있다.
4. 홈의 개인화 영역은 실제 `/me/recommendations`를 사용한다.
5. 추천 응답은 순위를 보존한 상품 카드 데이터와 추천 이유를 한 번에 반환한다.
6. 공개 최신 상품 경로를 추천으로 부르는 잘못된 계약을 단계적으로 제거한다.
7. 빈 결과, 인증 상태, 서버 오류를 서로 다른 UI로 표시하고 더미 데이터로 숨기지 않는다.

## 4. 비목표

- 외부 SNS 게시물 수집
- 마켓 게시글, 댓글, 채팅, 알림 시스템
- 마켓 피드 자체의 머신러닝 재정렬
- 비로그인 사용자의 익명 행동 기반 추천
- 추천 알고리즘 `hybrid_v1`의 가중치 변경
- 검색어 trending 집계 로직 고도화
- 셀러가 피드 노출을 별도로 구매하거나 예약하는 기능

## 5. 고객 경험

### 5.1 하단 메뉴와 경로

하단 메뉴는 다음 순서를 유지한다.

1. `카테고리` → `/categories`
2. `마켓 피드` → `/market-feed`
3. `오늘의 코디` → `/today-outfit`
4. `홈` → `/`
5. `좋아요` → `/likes`
6. `장바구니` → `/cart`
7. `마이페이지` → `/mypage`

`마켓 피드`에는 `Store` 계열 아이콘을 사용한다. 과거 `/snapshot` 링크는 북마크와 배포 캐시를 고려해 `/market-feed`로 리다이렉트한다. 트렌드관 UI와 트렌드 전용 E2E는 제거하고, 검색 화면의 인기 검색어 테스트는 유지한다.

### 5.2 로그인 회원의 마켓 피드

화면 상단은 `마켓 피드` 제목과 `팔로우한 마켓의 새로운 상품을 모아보세요` 설명을 표시한다. 피드 항목은 상품 등록 시각 내림차순이며 다음 내용을 가진다.

- 마켓 프로필 이미지, 이름, 마켓 상세 링크
- 상품 카드 전체 정보와 상품 상세 링크
- 상품 등록 시각
- 현재 팔로우 상태와 언팔로우 동작

첫 페이지는 20개를 요청하고 다음 커서가 있을 때만 추가로 불러온다. 동일 시각의 상품은 상품 ID 내림차순으로 안정적으로 정렬한다. 페이지 새로고침이나 다음 페이지 요청이 순위를 바꾸지 않도록 오프셋 대신 불투명 커서를 사용한다.

팔로우 해제에 성공하면 해당 마켓의 아직 화면에 보이는 항목을 즉시 제거하고 피드 쿼리를 무효화한다. 실패하면 항목을 유지하고 재시도 가능한 오류를 표시한다.

### 5.3 비로그인·빈 피드

비로그인은 개인 피드 API를 호출하지 않는다. 로그인 안내와 함께 `인기 마켓 둘러보기`를 표시하고 공개 마켓 목록을 팔로워 수 내림차순으로 보여 준다.

로그인했지만 팔로우한 마켓이 없으면 `관심 있는 마켓을 팔로우해 보세요` 상태와 인기 마켓을 표시한다. 팔로우는 기존 인증 API를 사용하며 성공 즉시 개인 피드를 다시 요청한다.

팔로우한 마켓은 있지만 판매 가능한 상품이 없으면 이를 별도 빈 상태로 안내하고 인기 마켓 목록을 피드 결과로 위장하지 않는다.

### 5.4 홈 추천

홈은 세션 복원이 끝나기 전 추천 요청을 시작하지 않는다.

- 로그인 회원: `GET /api/v1/me/recommendations?limit=12`를 호출한다.
- 배치 추천 결과가 있으면 `OOO님을 위한 추천 상품`으로 표시한다.
- 서버 응답의 모든 항목이 `source=FALLBACK`이면 `취향을 알아가는 동안 인기 상품을 보여드려요`로 표시한다.
- 비로그인은 `GET /api/v1/products/popular`를 호출하고 제목을 `지금 인기 있는 상품`으로 표시한다.
- 추천 API 오류를 인기 상품으로 조용히 대체하지 않는다. 오류와 재시도를 보여 줘 개인화 장애를 관찰할 수 있게 한다.

추천 결과는 현재 materialized 결과의 최대 수 안에서 한 번에 표시한다. 실제 추천 API에 없는 무한 스크롤과 offset 계약은 제거한다. 독립 `/recommendations` 페이지는 홈의 추천 섹션 앵커로 리다이렉트하고 햄버거 메뉴의 중복 `추천 상품` 항목은 제거한다.

## 6. 서버 설계

### 6.1 마켓 피드 모듈

`commerce-server/internal/marketfeed`를 읽기 전용 모듈로 추가한다. 이 모듈은 팔로우 관계와 상품 발행 순서를 조합하지만 마켓 팔로우 쓰기나 상품 쓰기를 소유하지 않는다.

구성요소는 다음 책임을 갖는다.

- `Repository`: 인증 회원이 팔로우한 공개 가능한 마켓의 판매 가능한 상품 ID와 정렬 키를 조회한다.
- `ProductLoader`: 조회된 ID의 공개 상품 카드 데이터를 일괄 로드한다.
- `Service`: 커서 검증, limit 정규화, 조회 순서 복원, 다음 커서 생성을 담당한다.
- `Handler`: 인증 컨텍스트에서 회원 ID를 가져오고 JSON 계약과 HTTP 오류를 처리한다.

조회는 `market_followers`, `markets`, `products`를 사용한다. 회원 ID는 URL이나 쿼리에서 받지 않고 인증 컨텍스트에서만 읽는다. 삭제된 상품, 판매 불가 상품, 공개 상태가 아닌 마켓, 현재 노출 제한을 받는 마켓은 제외한다. 상품 공개 판정은 기존 상품 목록의 공개 정책과 동일한 공용 predicate를 재사용해 정책이 갈라지지 않게 한다.

새 테이블과 비동기 피드 fan-out은 만들지 않는다. 현재 규모에서는 읽기 시점 fan-in 조회로 시작하고 `(member_id, market_id)` 팔로우 인덱스 및 상품의 `(market_id, created_at, id)` 조회 경로를 사용한다. 실행 계획에서 적절한 인덱스가 없으면 명시적 migration으로 추가한다.

### 6.2 마켓 피드 API

```http
GET /api/v1/me/market-feed?limit=20&cursor=<opaque>
Authorization: Bearer <token>
```

```json
{
  "items": [
    {
      "market": {
        "id": 10,
        "name": "마켓 이름",
        "profile_image_url": "https://...",
        "follower_count": 120
      },
      "product": {
        "id": 31,
        "market_id": 10,
        "market_name": "마켓 이름",
        "name": "상품 이름",
        "thumbnail_url": "https://...",
        "base_price": 39000,
        "discount_price": 29000
      },
      "published_at": "2026-09-05T10:00:00Z"
    }
  ],
  "next_cursor": "opaque-or-null"
}
```

`product`는 새 축약 타입을 만들지 않고 기존 공개 `ProductListItemResponse` 전체 계약을 재사용한다. 위 예시는 그중 피드 식별에 필요한 대표 필드만 표시한다.

`limit` 기본값은 20, 최댓값은 50이다. 커서는 서버가 인코딩한 UTC 상품 생성 시각과 상품 ID를 담고 클라이언트가 내부 값을 해석하지 않는다. 잘못된 커서는 구조화된 400 오류, 인증 부재는 401, 읽기 실패는 구조화된 5xx 오류로 응답한다. 회원별 응답은 `Cache-Control: private, no-store`를 사용한다.

### 6.3 공개 마켓 발견

기존 `GET /api/v1/markets`에 `sort=popular|new`를 추가한다. 기본값은 기존 호환성을 위해 `new`로 유지하고, `popular`는 `market_followers` 관계 테이블의 팔로워 수 내림차순과 마켓 ID 내림차순으로 정렬한다. 공개 가능하지 않은 마켓은 모든 정렬에서 제외한다. 웹의 기존 인기 마켓 화면과 마켓 피드 빈 상태는 `sort=popular`를 명시한다.

### 6.4 추천 응답 보강

`GET /api/v1/me/recommendations`의 배열 형태와 기존 추천 메타데이터는 유지하고 각 항목에 `product`를 추가한다.

```json
{
  "member_id": 7,
  "product_id": 31,
  "score": 42.5,
  "rank": 1,
  "reason_code": "SIMILAR_TAGS",
  "reason_text": "최근 관심 태그와 유사한 상품",
  "algorithm": "hybrid_v1",
  "source": "BATCH",
  "generated_at": "2026-09-05T09:00:00Z",
  "expires_at": "2026-09-06T09:00:00Z",
  "product": {
    "id": 31,
    "market_id": 10,
    "market_name": "마켓 이름",
    "name": "상품 이름",
    "thumbnail_url": "https://...",
    "base_price": 39000,
    "discount_price": 29000
  }
}
```

여기서도 `product`는 마켓 피드와 동일한 공개 `ProductListItemResponse` 전체 계약이다.

추천 서비스에는 공개 상품 요약을 일괄 로드하는 좁은 인터페이스를 주입한다. 추천 순서대로 상품을 복원하고, 더 이상 공개할 수 없는 상품은 제외한다. 상품별 추가 요청은 하지 않는다. 결과가 비어 있을 때의 기존 인기 상품 fallback은 유지하며 `source=FALLBACK`으로 구분한다.

### 6.5 잘못된 공개 추천 경로 폐기

배포 순서 충돌을 피하기 위해 다음 순서로 제거한다.

1. 서버가 마켓 피드와 상품이 포함된 회원 추천 응답을 먼저 배포한다.
2. 웹에서 `/api/v1/products/recommendations` 사용을 모두 제거하고 홈을 새 계약으로 전환한다.
3. 웹 배포 후 서버 접근 로그에서 7일 동안 레거시 경로 호출이 없음을 확인한다.
4. 서버에서 `GET /api/v1/products/recommendations` 라우트와 계약 테스트를 제거한다.

레거시 경로 유지 기간에도 새 코드나 CMS 매핑은 이 경로를 추천으로 취급하지 않는다. 이 경로가 필요했던 최신 상품 구좌는 명시적인 `/api/v1/products/latest`를 사용한다.

## 7. 웹 설계

- `src/components/app-shell.tsx`: 트렌드관을 마켓 피드로 교체하고 중복 추천 메뉴를 제거한다.
- `src/app/market-feed/page.tsx`: 마켓 피드 라우트 진입점이다.
- `src/components/market-feed-page.tsx`: 인증 상태, 커서 페이지, 빈 상태, 마켓 발견, 팔로우 동작을 조합한다.
- `src/lib/api/market-feed.ts`: 마켓 피드와 `markets?sort=popular` 계약을 검증한다.
- `src/components/home-page.tsx`: 사용자 작업 중인 이벤트 캐러셀 변경을 보존하면서 추천 query 부분만 실제 회원 추천으로 바꾼다.
- `src/lib/api/customer.ts`: 상품을 필수로 갖는 회원 추천 응답 스키마를 사용하고 limit를 전송한다.
- `src/lib/api/catalog.ts`: 공개 `listRecommendedProducts`를 제거한다.
- `src/app/snapshot/page.tsx`: `/market-feed` 리다이렉트로 교체한다.
- `src/app/recommendations/page.tsx`: 홈 추천 섹션으로 리다이렉트한다.

홈 추천 상품 카드에는 서버가 제공한 `product`만 사용한다. 상품 데이터가 없는 계약 위반 항목을 부분 렌더링하지 않고 응답 검증 오류로 처리한다. 추천 이유는 카드 본문을 복잡하게 만들지 않도록 섹션 설명과 접근 가능한 보조 텍스트에 사용한다.

## 8. 오류 처리와 운영 안전성

- 마켓 피드의 401은 전역 세션 만료 흐름을 따르고, 토큰이 처음부터 없는 경우에는 정상 비로그인 상태를 표시한다.
- 개인 피드와 개인 추천 오류를 공개 인기 데이터로 위장하지 않는다.
- 마켓을 언팔로우할 때 낙관적 제거를 적용하되 실패하면 이전 캐시를 복구하고 오류를 표시한다.
- 다음 페이지 실패는 기존 항목을 유지하고 하단에 재시도 동작을 제공한다.
- 삭제·숨김·품절·제재 상태는 조회 시점에 다시 판정한다.
- 서버 로그에 원문 토큰이나 불투명 커서 내부 값을 남기지 않는다.
- 개인 피드 요청 수, 지연 시간, 오류율, 빈 피드 비율과 홈 추천의 `BATCH`/`FALLBACK` 비율을 관찰 가능하게 한다.

## 9. 테스트 전략

### 9.1 서버

- 인증 회원 이외의 팔로우 관계가 섞이지 않는지 검증한다.
- 판매 불가 상품과 공개 불가·제재 마켓이 제외되는지 검증한다.
- `(created_at, id)` 커서에서 중복과 누락 없이 다음 페이지가 이어지는지 검증한다.
- 기본·최대 limit 및 잘못된 커서 오류를 검증한다.
- `markets?sort=popular`가 관계 테이블의 팔로워 수를 사용하고 안정적인 tie-break를 갖는지 검증한다.
- 추천 상품 일괄 로드가 순위를 보존하고 비공개 상품을 제거하는지 검증한다.
- 추천 fallback과 배치 결과 모두 `product`, `source`, `reason_code`를 반환하는지 검증한다.
- 데이터베이스 통합 테스트에서 feed 쿼리의 인덱스 사용과 최대 쿼리 수를 확인한다.

### 9.2 웹

- 마켓 피드와 회원 추천 Zod 계약 테스트
- 비로그인, 팔로우 없음, 팔로우 상품 없음, 정상 피드, 첫 페이지 실패, 다음 페이지 실패 상태
- 팔로우·언팔로우 성공과 실패 시 캐시 동기화
- 로그인 회원은 `/me/recommendations`, 비로그인은 `/products/popular`만 호출하는 홈 테스트
- `BATCH`와 `FALLBACK`에 맞는 홈 제목
- `/snapshot` 및 `/recommendations` 리다이렉트
- 모든 뷰포트에서 7개 하단 메뉴와 `마켓 피드` 활성 상태
- 기존 이벤트 캐러셀 자동 재생 테스트와의 회귀 없음

### 9.3 품질 검증

- 서버: 관련 패키지 단위 테스트, 전체 `go test ./...`, 정적 검사, API 계약 테스트
- 웹: 단위 테스트, lint, production build, 관련 Playwright E2E
- 390x844, 1024x768, 1440x900에서 로딩·빈 상태·피드·추가 로딩 스크린샷 확인
- 개인 피드 응답이 공유 캐시에 저장되지 않는지 헤더 확인

## 10. 배포 순서

1. 서버 additive 변경: 마켓 피드, 마켓 정렬, 추천 상품 응답 보강
2. 서버 계약과 DB 실행 계획 검증
3. 웹 전환: 마켓 피드 UI, 하단 메뉴, 홈 실제 추천, 레거시 화면 리다이렉트
4. 배포 환경 E2E로 로그인·비로그인 경로 확인
5. 7일간 레거시 `/products/recommendations` 호출량 관찰
6. 호출이 없으면 서버에서 레거시 라우트 제거

서버가 먼저 배포되어도 기존 웹 응답은 깨지지 않고, 웹이 전환된 뒤에도 레거시 라우트 제거 전까지 롤백이 가능하다.

## 11. 완료 기준

- 하단 메뉴에 트렌드관 대신 마켓 피드가 표시되고 `/market-feed`로 이동한다.
- 로그인 회원은 자신이 팔로우한 공개 마켓의 판매 가능한 신상품만 최신순으로 본다.
- 비로그인·무팔로우·무상품·오류 상태가 구분된다.
- 홈의 로그인 추천은 실제 `/me/recommendations`와 상품 카드 데이터를 사용한다.
- 홈의 비로그인 영역은 개인화 문구 없이 인기 상품을 사용한다.
- 웹 런타임에서 `/api/v1/products/recommendations` 호출이 없다.
- 검색 화면의 인기 검색어는 유지되며 독립 트렌드관 UI는 제거된다.
- 기존 사용자의 이벤트 캐러셀 변경과 다른 미관련 작업은 보존된다.
- 모든 관련 서버·웹 테스트와 production build가 통과한다.
